# Как работает JWT-авторизация — простым языком

## 🎯 Зачем нужна авторизация?

Сервер не помнит кто ты. Каждый HTTP-запрос — это как новый звонок от незнакомца. Нужен способ **доказать серверу**, что ты — это ты.

---

## 🔑 Что такое JWT-токен?

**JWT (JSON Web Token)** — это зашифрованная строка, внутри которой лежит информация о пользователе:

```
eyJ0eXAiOiJKV1QiLCJhbGciOiJIUzI1NiJ9.eyJ1c2VyX2lkIjo1fQ.abc123...
```

Если расшифровать, внутри будет:
```json
{
  "user_id": 5,
  "exp": 1710000000    ← срок годности токена
}
```

Токен **подписан секретным ключом** сервера — подделать его невозможно.

---

## 📋 Полный цикл авторизации

```
┌─────────────┐                          ┌─────────────┐
│  ФРОНТЕНД   │                          │   БЭКЕНД    │
│  (браузер)  │                          │   (сервер)  │
└──────┬──────┘                          └──────┬──────┘
       │                                        │
       │  1. POST /api/auth/login/              │
       │  { email, password }                   │
       │ ────────────────────────────────────►   │
       │                                        │  ✔ Проверяет email/пароль
       │                                        │  ✔ Генерирует JWT-токен
       │   2. { access: "eyJ...", refresh: "eyJ..." }
       │  ◄────────────────────────────────────  │
       │                                        │
       │  💾 Сохраняет токен                    │
       │  (localStorage / cookie)               │
       │                                        │
       │  3. GET /api/users/profile/            │
       │  Header: Authorization: Bearer eyJ...  │
       │ ────────────────────────────────────►   │
       │                                        │  ✔ Достаёт токен из заголовка
       │                                        │  ✔ Расшифровывает → user_id=5
       │                                        │  ✔ Отдаёт данные юзера 5
       │   4. { phone: "...", address: "..." }  │
       │  ◄────────────────────────────────────  │
```

## 🧱 Кто за что отвечает?

| Компонент | Роль | Аналогия |
|---|---|---|
| **Фронтенд** | Хранит и отправляет токен | 📦 Курьер — носит пропуск |
| **Бэкенд** | Проверяет токен, решает пускать или нет | 🛡 Охранник — проверяет пропуск |
| **JWT-токен** | Удостоверение личности | 🎫 Пропуск |

> ⚠️ Фронтенд **не решает**, есть ли у юзера права. Он просто передаёт токен. Решение принимает **только бэкенд**.

---

## 📨 Заголовок Authorization

Это **HTTP-заголовок**, который фронтенд добавляет к каждому запросу:

```
GET /api/users/profile/ HTTP/1.1
Host: localhost:8000
Authorization: Bearer eyJ0eXAiOiJKV1QiLCJhbGciOiJIUzI1NiJ9...
Content-Type: application/json
```

Формат: `Bearer` + пробел + токен.

---

## 🔄 Access и Refresh токены

| Токен | Срок жизни | Назначение |
|---|---|---|
| **Access** | 60 минут | Для запросов к API |
| **Refresh** | 7 дней | Для получения нового access-токена |

Зачем два? Чтобы не заставлять юзера логиниться каждый час:

```
Access истёк (прошло 60 мин)
    ↓
POST /api/auth/refresh/  { refresh: "eyJ..." }
    ↓
Получил новый access-токен → работаем дальше
```

## 🔓 AllowAny vs IsAuthenticated

В Django REST Framework для каждого endpoint задаётся **политика доступа**:

```python
# Любой может обращаться, даже без токена
'DEFAULT_PERMISSION_CLASSES': ['rest_framework.permissions.AllowAny']

# Только авторизованные (с валидным токеном)
'DEFAULT_PERMISSION_CLASSES': ['rest_framework.permissions.IsAuthenticated']
```

### В нашем проекте:

| Сервис | Настройка | Что значит |
|---|---|---|
| **product-service** | `AllowAny` | Токен НЕ нужен — любой может создавать товары |
| **user-service** | `AllowAny` по умолчанию, но `profile/` защищён JWT | Регистрация/логин открыты, профиль — только с токеном |

## 🧪 Как тестировать в Postman

### Способ 1: Вкладка Authorization (рекомендуется ✅)

```
Вкладка Authorization → Type: Bearer Token → вставить токен
```

Postman сам добавит заголовок `Authorization: Bearer <token>`.

### Способ 2: Вкладка Headers (вручную)

```
Key: Authorization
Value: Bearer eyJ0eXAiOiJKV1Qi...
```

> 💡 Оба способа делают **одно и то же** — отправляют HTTP-заголовок. Вкладка Authorization просто удобнее.

---

## 🚫 Что будет без токена?

Если эндпоинт защищён (`IsAuthenticated`) и ты не передашь токен:

```json
{
    "detail": "Authentication credentials were not provided."
}
```

HTTP-статус: `401 Unauthorized`

---

## 📝 Итого: чеклист для понимания

- [ ] JWT — это зашифрованная строка с данными юзера
- [ ] Фронтенд хранит токен и отправляет его в заголовке `Authorization`
- [ ] Бэкенд проверяет токен и решает — пускать или нет
- [ ] Access-токен живёт 60 мин, refresh — 7 дней
- [ ] `AllowAny` = без токена, `IsAuthenticated` = нужен токен
- [ ] В Postman можно передать токен через вкладку Authorization или Headers — разницы нет
